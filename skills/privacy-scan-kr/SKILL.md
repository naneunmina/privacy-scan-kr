# 한국 개인정보보호법 준수 스캔

이 스킬은 **바이브코딩으로 빠르게 만들어진 프로젝트**가 한국 개인정보 보호법(PIPA)
관점에서 놓치기 쉬운 부분을 잡아내기 위한 것입니다. 코드 생성에 개입하지 않고,
이미 작성된 코드를 읽고 분석하는 **스캔형** 도구입니다.

## 면책 조항 (반드시 스캔 결과 맨 위에 포함할 것)

이 스캔은 법률 자문이 아니며 참고용입니다. 실제 서비스 출시 전 법률 전문가의
검토를 받으시길 권장합니다. 이 스킬은 코드에서 확인 가능한 패턴만
탐지하며, 실제 운영 방식(오프라인 수집, 제3자 계약 내용, 내부 정책 등)까지는
알 수 없습니다.

## 동작 원리: 2단계 워크플로우

**절대 원칙: 사용자가 명시적으로 승인하기 전까지는 절대 처리방침/이용약관/동의
UI를 생성하거나 코드에 삽입하지 않는다.** 1단계(스캔)와 2단계(문서 생성)는
분리된 작업이며, 사용자가 "처리방침 만들어줘", "동의 체크박스 추가해줘" 등으로
명확히 요청해야 2단계로 넘어간다. 스캔 결과를 보여주는 것과 동시에 알아서
문서를 만들어 붙이지 말 것 — 사용자가 스캔 결과만 보고 싶을 수도 있다.

---

## 1단계: 스캔

### 1-1. 스택 자동 판단

프로젝트 루트와 하위 디렉토리를 훑어서 어떤 기술 스택인지 스스로 판단한다.
특정 프레임워크로 범위를 한정하지 않는다. 판단 근거 예시:

- `package.json` → dependencies로 React/Vue/Next.js/Express/NestJS 등 구분
- `requirements.txt`, `pyproject.toml`, `manage.py` → Django/Flask/FastAPI
- `pom.xml`, `build.gradle` → Spring
- `go.mod` → Go
- `Gemfile` → Rails
- 없으면 파일 확장자(.tsx, .vue, .py, .java, .go, .rb 등)로 추정

스택을 알면 어디를 봐야 할지 좁힐 수 있다 (예: Django면 `models.py`와
`forms.py`, Next.js면 API routes와 폼 컴포넌트, Spring이면 Entity/DTO 클래스).
하지만 스택 판단에 시간을 오래 쓰지 말 것 — 결국 목적은 아래 1-2의 패턴을
찾는 것이다.

### 1-2. 개인정보 수집·이용 지점 탐지

넓게 잡는 것이 원칙이다 (과소탐지보다 과잉탐지가 안전). 아래 패턴들을 Grep과
Read로 훑어본다. 이건 고정된 정규식 엔진이 아니라 시작점이니, 프로젝트 맥락에
맞게 유연하게 판단할 것.

**a) 개인정보를 받는 모든 입력 폼 — 회원가입만이 아니다**
- 이름, 이메일, 전화번호, 생년월일, 주소, 주민등록번호, 성별 등을 받는
  `<input>`, `<form>`, 폼 상태(useState, reactive, formik, react-hook-form 등)
- 회원가입/프로필 API 엔드포인트의 request body 필드
- ⚠️ **회원가입·로그인 폼만 찾고 끝내지 말 것.** 아래도 똑같이 개인정보
  수집 지점이며, 놓치기 훨씬 쉽다: 문의하기/1:1 상담/고객센터(CS) 폼,
  뉴스레터·마케팅 수신 신청, 이벤트/프로모션 응모, 설문조사·피드백 폼,
  예약·신청·견적 요청 폼. `contact`, `inquiry`, `support`, `feedback`,
  `survey`, `apply`, `subscribe` 등의 이름을 가진 컴포넌트·라우트도 반드시
  확인할 것. 문의하기/CS 폼은 오히려 회원가입보다 위험도가 높은 경우가
  많다 — 이유는 [rules/consent-basics.md](rules/consent-basics.md)의
  "또 다른 흔한 함정 — 문의하기/CS 폼" 참고.

**b) 데이터 저장 스키마**
- DB 모델/스키마 정의 (Prisma `schema.prisma`, Django `models.py`, Mongoose
  schema, TypeORM entity, SQL migration 파일)에서 개인정보성 컬럼명
  (email, phone, name, address, birth, ssn, gender 등)

**c) OAuth / 소셜 로그인**
- next-auth, passport, firebase-auth, 카카오/구글/네이버/애플 SDK 설정
- 자세한 판단 기준은 [rules/oauth-social-login.md](rules/oauth-social-login.md) 참고

**d) 분석/마케팅/트래킹 SDK**
- Google Analytics, Meta Pixel, 카카오 픽셀, Mixpanel, Amplitude, 이메일
  마케팅(Sendgrid, Mailchimp 등) 연동 코드 — 사용자 행동 데이터 수집으로 간주

**e) 쿠키 / 로컬스토리지에 개인정보 저장**

**f) 만 14세 미만 아동 관련**
- 생년월일/나이 수집 필드는 있는데 나이 확인·법정대리인 동의 로직이 없는 경우
- 자세한 기준은 [rules/minors.md](rules/minors.md) 참고

**g) 제3자 제공**
- 외부 API/서비스로 사용자 데이터를 전송하는 코드 (analytics, CRM, 결제,
  배송대행 등)

**h) 기존 준수 장치 확인**
- 처리방침/이용약관 페이지나 마크다운 파일 존재 여부 (`privacy-policy`,
  `terms`, `개인정보처리방침` 등 이름으로 검색)
- 동의 체크박스 UI 컴포넌트 존재 여부 — **위 (a)에서 찾은 개인정보 수집 폼
  각각의 근처**를 확인한다 (회원가입 폼뿐 아니라 문의하기/CS/뉴스레터
  구독 등 모든 폼 개별적으로 확인. 회원가입 폼에만 동의 체크박스가 있고
  문의하기 폼에는 없는 경우가 실무에서 흔하다 — 폼마다 따로 판단할 것)
- 만약 처리방침은 있는데 동의 체크박스/절차가 전혀 없다면, 그 자체가 경고
  대상이다 — 처리방침은 현황을 공시하는 문서일 뿐 동의를 받는 절차가 아니다.
  [rules/privacy-policy-items.md](rules/privacy-policy-items.md) 참고.

### 1-3. 심각도 판정

각 발견 사항에 심각도를 매긴다. 판단 근거는 [rules/consent-basics.md](rules/consent-basics.md),
[rules/privacy-policy-items.md](rules/privacy-policy-items.md),
[rules/oauth-social-login.md](rules/oauth-social-login.md),
[rules/minors.md](rules/minors.md)에 있는 조문과 기준을 따른다.

- **HIGH**: 개인정보 수집이 명확한데 동의 절차나 처리방침 관련 코드가 전혀
  없음. 예: 이메일/전화번호를 받는 회원가입 폼이 있는데 동의 체크박스도
  처리방침 링크도 없음. **"이용약관 동의" 체크박스만 있고 개인정보 수집·이용
  동의 문구는 없음**(체크박스가 있다고 곧바로 "동의 UI 있음"으로 넘겨짚지
  말 것 — [rules/consent-basics.md](rules/consent-basics.md)의 "가장 흔한
  함정" 참고, 실무에서 매우 자주 나오는 패턴이다). OAuth로 받은 이메일을
  마케팅 발송에 쓰는데 별도 동의가 없음. 생년월일을 수집하는데 나이 검증·
  법정대리인 동의 로직이 코드 어디에도 없음(생년월일 필드만 있고 그 값을
  실제로 읽어서 분기하는 로직이 전혀 없는 경우도 포함).
- **MEDIUM**: 애매한 경우. 예: 닉네임처럼 그 자체로는 개인 식별이 어려운
  정보만 수집하지만 다른 정보(이메일 등)와 결합될 여지가 있음. 수집 목적이
  코드만으로는 불분명함. 동의 체크박스는 있는데 처리방침 링크가 없거나 그
  반대. 처리방침은 있는데 실제 코드에서 수집하는 항목과 처리방침에 적힌
  항목이 달라 보임.

애매하면 HIGH보다 MEDIUM 쪽으로, 그리고 왜 애매한지 이유를 함께 적을 것 —
사용자가 스스로 판단할 근거를 줘야 한다.

### 1-4. 결과 출력 형식

스캔이 끝나면 아래 구조로 보여준다. **이 단계에서는 코드나 문서를 생성하지
않는다.**

```
## 개인정보보호법 스캔 결과

(면책 문구 한 줄)

### 🔴 HIGH
- `path/to/file.tsx:23` — 무엇을 발견했는지, 왜 문제인지, 관련 조항(rules/*.md 참조)

### 🟡 MEDIUM
- `path/to/file.py:45` — ...

### 참고: 발견하지 못한 항목
(스캔이 커버하지 못하는 부분이 있다면 명시 — 예: 오프라인 수집, 서버 로그 등은
코드만으로 알 수 없음)

---
처리방침/이용약관/동의 UI 초안이 필요하면 말씀해주세요. 위에서 실제로 발견된
수집 항목을 근거로 만들어 드릴 수 있습니다.
```

**HIGH·MEDIUM이 하나도 없을 때**: 위 형식을 억지로 채우지 말고, 개인정보를
수집하는 지점이 없었는지 아니면 있었지만 동의·처리방침이 이미 갖춰져 있었는지를
명확히 구분해서 짧게 알려준다. 이미 잘 갖춰진 경우, 발견한 근거(어느 파일에
어떤 동의 UI·처리방침이 있었는지)를 한두 줄로 밝힌다. 이 경우 "처리방침 초안이
필요하면 말씀해주세요" 같은 문서 생성 제안 문구는 이미 있는 걸 다시 만들라는
것처럼 들리므로 붙이지 않는다.

## 2단계: 문서 생성 (사용자 승인 후에만)

사용자가 "처리방침 만들어줘", "동의 체크박스 추가해줘" 등으로 승인하면
진행한다.

1. **반드시 1단계 스캔에서 실제로 발견된 수집 항목을 근거로 채운다.** 스캔하지
   않은 항목을 추측해서 넣지 말 것. 스캔 결과에 없는 항목이 필요하면(예: 수집
   목적, 보유 기간처럼 코드만으로 알 수 없는 정보) 사용자에게 물어본다.
2. 템플릿은 [templates/privacy-policy.md](templates/privacy-policy.md),
   [templates/terms-of-service.md](templates/terms-of-service.md)를 사용한다.
   `{{변수}}` 형태의 자리표시자를 스캔 결과와 사용자 답변으로 채워서 완성한다.
   [rules/privacy-policy-items.md](rules/privacy-policy-items.md)의 필수
   기재 항목 체크리스트를 참고해서 빠진 항목이 없는지 확인한다.
3. 동의 체크박스 UI는 [templates/consent-checkbox.md](templates/consent-checkbox.md)에서
   프로젝트 스택에 맞는 컴포넌트 예시(React/Vue/plain HTML)를 골라 적용한다.
   회원가입 폼 근처에 실제로 삽입하기 전에 어디에 넣을지 사용자에게 확인한다
   (기존 폼 구조를 깨뜨릴 수 있으므로).
4. 만 14세 미만 아동 대상 서비스로 보이면 [rules/minors.md](rules/minors.md)의
   법정대리인 동의 절차를 반영한다.
5. 생성된 모든 문서 하단에 "이 초안은 법률 전문가의 검토를 권장합니다"라는
   문구를 포함한다 (템플릿에 이미 포함되어 있음).

## 판단 원칙 요약

- OAuth 소셜 로그인(카카오/구글/네이버/애플 등)을 쓰더라도 **처리방침 게시**는
  개인정보 보호법 제30조에 근거한 내 서비스의 의무이며, OAuth 동의창(제공자와
  이용자 사이의 별도 동의)이 이를 대체하지 않는다. 반면 **이용약관 동의**는
  개인정보 보호법 소관이 아니라 전자상거래법·약관법 등 계약법 영역의 일반
  실무이므로, 스캔 결과에서 이 둘을 같은 법적 근거로 묶어 설명하지 말 것 —
  자세한 내용은 [rules/oauth-social-login.md](rules/oauth-social-login.md)의
  "중요한 정정" 항목 참고.
- OAuth로 받은 정보를 로그인 목적을 벗어나 사용(마케팅, 분석, 제3자 제공 등)
  하면 개인정보 보호법 제18조·제22조에 따라 별도의 수집·이용 동의가 필요하다
  (강한 법적 근거).
- 처리방침(제30조, 공시 의무)은 동의(제15조·제22조, 수집 근거)를 받는 문서가
  아니라 현황을 공시하는 문서다. "처리방침만 있고 별도 동의 절차가 없는
  경우"도 경고 대상이다.
- 벌칙 정보를 사용자에게 안내할 때는 위반 유형별로 근거 조항과 금액이 다르다는
  점을 반드시 정확히 전달할 것. "동의 방법 위반 = 5천만원 이하 과태료" 같은
  식으로 뭉뚱그리지 말 것 (실제로는 위반 유형에 따라 1천만원~5천만원 사이에서
  갈리고, 형사처벌과 과태료가 별개로 적용되는 경우도 있다). 각 rules/*.md의
  벌칙표를 그대로 인용할 것.

각 원칙의 법적 근거와 조문 원문은 `rules/` 아래 각 파일에 있다. 스캔 중
판단이 애매하면 그 파일들을 먼저 열어서 확인할 것.
